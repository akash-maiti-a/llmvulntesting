01

The problem it solves

Static analyzers are high-recall and low-precision: they find most real bugs but bury them under false alarms, so engineers stop reading the output. vulnscan keeps the analyzers' recall and adds a triage layer that removes noise — then proves the trade-off on labelled code instead of trusting the model.

Detect

Three analyzers

Semgrep registry rulesets and custom taint rules for PHP and Python, plus Pysa for inter-procedural Python taint. Each finding is normalized into one Finding model.

Triage

A local LLM judge

Each alert is sent on its own to a local model via Ollama, constrained to a JSON schema, and labelled true_positive or false_positive with a reasoned analysis.

Measure

Scored on ground truth

Deliberately vulnerable apps, a 38-case synthetic benchmark, and real CVEs (vulnerable vs. patched) give a label for every region, so precision and recall are real numbers.

03

How it works

Six stages, each a small, testable module.

01 · Targets

Reproducible by construction

Every codebase is pinned to a commit SHA in targets.yaml. CVE targets expand automatically into a @vuln and a @fixed variant around the fix commit, so the same tool is tested on the bug and on its patch.

02 · Scanning

Taint with traces

Semgrep runs twice (registry + custom) with --dataflow-traces, so each finding carries its source → sink path; its taint is intra-procedural. Pysa follows taint across functions and files for Python, resolving library calls through pinned models.

03 · Findings & CWE

One model, stable IDs

Every engine emits the same Finding (tool, ruleset, CWE, file, lines, snippet, trace) with a stable sha1 id. Tools name the same bug with different CWEs, so CWEs are grouped into families (sqli, cmdi, xss…) and matched by family.

04 · LLM triage

Structured, schema-bound verdicts

Each alert goes to Ollama at temperature 0 with a JSON-schema reply. Prompts evolved v1 → v2 → v3: v2 forces the model through sink_is_real, attacker_reaches_sink, and defence_sufficient; v3 makes it write the analysis before committing to the checks. File paths are redacted so benchmark names can't leak the answer.

05 · Ground truth

Every region has a label

Per-target YAML marks each location vulnerable: true|false with a CWE and scope (taint, other, client). CVE truth is derived mechanically from the fix diff — the lines the patch changed are the vulnerable ones.

06 · Evaluation

Honest, fail-open scoring

A finding hits an entry when it lands in its location and shares its CWE family. The evaluator reports recall per scope, precision, false positives on known-safe code, and triage accuracy. Timeouts and bad replies are kept, never silently dropped (fail open).

⌁
Fast vs. reasoning. The fast pass answers in ~2–11s per alert. A ~7× slower chain-of-thought pass is used only as a second tier on alerts the fast pass rejected — a two-tier policy that recovers recall without paying the reasoning cost on every alert.

05

Fine-tuning the triage model

A research track (round 3) trains a smaller, specialized triage model with reinforcement learning, so the project doesn't depend on an 8B general model for inference.

Method

GRPO on Qwen3-4B

A 4-bit Qwen3-4B base with a LoRA adapter (0.81% of parameters trained) is tuned with GRPO: the model samples several verdicts per alert, and the policy is pushed toward the higher-reward ones. Runs in an isolated GPU container on an 8 GB laptop card.

Reward

More than "right answer"

Each reply is scored on four terms — valid JSON, correct verdict (missing a real bug penalized 4× harder than keeping noise), calibration (Brier score of its confidence), and consistency between its checks and verdict.

Data

Held out from evaluation

955 training / 111 dev alerts are built from a separate set of vulnerable apps and suites, with label-leaking comments and variable names scrubbed and a whitespace-hash check that aborts on any overlap with an evaluation file.

Status

Pipeline validated

A 10-step smoke run completed end-to-end — base model loaded, LoRA attached, all steps ran, adapter saved — and the scanner's unit suite passes 34/34. A full multi-epoch run is the next step; the fine-tuned model is not yet claimed to beat the 8B base.

06

Engineering notes

Choices made so the results are trustworthy and the project is easy to run.

  • Reproducible everything. Targets pinned to SHAs; Semgrep 1.95.0 and Pyre 0.9.23 pinned in a Docker image; verdicts cached per finding id so runs resume and repeat.
  • No data leakage. File paths are redacted in prompts, hint comments are blanked while preserving line numbers, and training data is hash-checked against every evaluation file.
  • Fail open. A timed-out or malformed triage reply keeps the finding rather than dropping it — the scanner never hides a bug because the model stumbled.
  • Local & private. The LLM runs on the host through Ollama; nothing is sent to a third-party API.
  • Tested. A pytest suite covers the parsers, CVE fix-diff ground truth, CWE matching, scoring, triage, and the RL reward — 34 tests, green.
  • One command to run it all. docker compose run --rm scanner vulnscan run fetches, scans, triages, and evaluates into results/report.md.

RUN IT YOURSELF

# host: Ollama with the triage model
ollama pull qwen3:8b
ollama serve

# scan + triage + evaluate every target
docker compose build
docker compose run --rm scanner vulnscan run
# → results/summary.json, results/report.md
